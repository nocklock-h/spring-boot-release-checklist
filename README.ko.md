## 왜 이 체크리스트를 만들었을까?

작은 Spring Boot 제품을 만들고 배포하면서 느낀 점이 있습니다.

어려운 건 기능을 하나 더 개발하는 일이 아닐 때가 많았습니다.

오히려 이런 질문에 답하는 일이 더 어려웠습니다.

- 운영 환경 설정을 제대로 검증했을까?
- 비밀번호와 API Key 같은 민감정보가 애플리케이션에서 분리되어 있을까?
- 배포 후에도 사용자의 핵심 기능이 정상적으로 동작할까?
- 이번 배포가 정상적이라는 증거는 무엇일까?
- 문제가 발생하면 어느 버전으로 되돌릴 수 있을까?
- AI가 알려준 답을 믿고 있는 걸까, 아니면 직접 확인한 걸까?

이 저장소는 배포 전에 이런 질문을 하나씩 확인하기 위해 만든 작은 점검 워크플로입니다.

### 2. 증거 기반 AI 검토

AI를 배포 여부를 결정하는 주체가 아니라, 두 번째 검토자로 활용합니다.

단순히 AI에게 이렇게 묻는 대신,

> "이 애플리케이션은 운영 환경에 배포할 준비가 되었나요?"

각 판단에 대한 증거를 요구하도록 합니다.

예를 들어 다음과 같은 프롬프트를 사용할 수 있습니다.

```
이 Spring Boot MVP의 출시를 막을 수 있는 문제를 검토해줘.

각 점검 항목에 대해:

1. 무엇을 확인해야 하는지 설명해줘.
2. 관련 파일, 설정, 명령어 실행 결과 또는
   그 밖의 검증 증거를 제시해줘.
3. VERIFIED 또는 NOT VERIFIED로 표시해줘.
4. 어떤 문제가 출시를 막는지 설명해줘.

증거가 없다는 이유로 안전하다고 가정하지 마.
내가 요청하지 않는 한 코드를 수정하지 마.
```

여기서 구분해야 할 것은 다음 두 가지입니다.

> **증거(Evidence) ≠ 추론(Inference)**

확인할 증거가 없다면 다음과 같이 기록합니다.

```
NOT VERIFIED
```

저장소에 포함된 프롬프트도 활용할 수 있습니다.

### 3. 배포 검증 기록 템플릿

모든 MVP에 복잡한 배포 관리 시스템이 필요한 것은 아닙니다.

다음 정도의 기록만으로도 시작할 수 있습니다.

```
배포 커밋:
운영 서비스 URL:
클린 빌드 검증 결과:
테스트 검증 결과:
운영 환경 설정 검토 여부:
핵심 사용자 기능 검증:
롤백 기준점:
현재 해결되지 않은 위험:
```

실제 기록 예시는 다음과 같습니다.

```
./gradlew clean build → BUILD SUCCESSFUL
./gradlew test → 예상한 테스트 통과
Release commit → a1b2c3d
Deployment ID → 배포 플랫폼의 릴리스 식별자
Health check → 운영 URL에서 예상 응답 확인
Critical flow → 운영 환경에서 핵심 기능 수동 검증
Rollback point → 이전 정상 커밋 또는 배포 버전
```

> 배포 검증 기록에 비밀번호, API Key, 토큰, 기타 민감정보나 사용자의 개인정보를 저장하지 마세요.

반복해서 사용할 수 있는 템플릿도 제공합니다.

## 배포에 대한 생각

이 저장소에서 가장 강조하고 싶은 것은 하나입니다.

> **배포 성공과 출시 검증 완료는 같은 의미가 아닙니다.**

배포 플랫폼에서 초록색 성공 표시가 나타났다면 배포 프로세스가 완료되었다는 뜻입니다.

하지만 그것만으로 다음 사항까지 증명되지는 않습니다.

- 운영 환경 설정이 올바른지
- 외부 시스템 연동이 정상적으로 작동하는지
- 사용자의 핵심 이용 흐름이 정상적인지
- 민감정보가 안전하게 관리되는지
- 문제가 발생했을 때 롤백할 수 있는지
- 실제 배포된 버전이 의도한 버전과 일치하는지

MVP의 배포 과정이 반드시 복잡할 필요는 없습니다.

다만 중요한 가정들을 눈으로 확인할 수 있어야 합니다.
